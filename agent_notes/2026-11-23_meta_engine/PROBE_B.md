# Probe B: rows read rows

`DESIGN.md` §5 (capability R), §5.3 (the read rule), §8 P2 and P3. Written before any code;

## 1. What a user writes

```
kind Leg @World (actor: Trunk, site: u, socket_x: f, …, anchor_x: m, …, toe_z: m) {
  visible(ro, rd) = hit_min(hit_min(ray_capsule(ro, rd, hip, knee, 0.054), ray_capsule(ro, rd, knee, toe, 0.036)), …)
  trace(p) = min(capsule(p, hip, knee, 0.054), …)
  material(p, n) {
    let t = Trunk[actor]                          # a query reads another kind through a row reference
    let height = (inv(t.deck_pose) * p).y
    ggx(mix(t.paint * 0.36, t.paint, smoothstep(0.07, 0.63, height)), 0.39, 0.0) + coat(0.32, 0.13)
  }
}

pub law stride(t: Trunk, dt: s, legs: [Leg]) writes t.{x, z, …, lifter} {
  for i in 0..8 { if i < t.leg_count { let l = legs[t.first_leg + i] … } }   # the parent loops its legs
}
pub law swing(l: Leg, dt: s, trunks: [Trunk]) writes l.{anchor_x, …, toe_z} {
  let t = trunks[l.actor]                         # the leg reads its parent, as `stride` just left it
}
```

A body plan is the number of `Leg` rows the build emits. There is no `sites` lane packing in rows
and no `_a`/`_b` pairs in the kinds (the gait still packs eight legs into v4 lanes *inside* the
trunk law so it can reuse `hull`/`contact` unchanged).

## 2. Lowering plan

### 2.1 Checker (`loft-check`)

- `[K]` parameters on laws and checks already type as `Ty::Table(K)`; indexing required an `Id(K)`.
  Indexing now also takes `u32` (a contiguous child range is `first + i`).
- In a kind query, `K[i]` where `K` names a kind and is not a local types the base as
  `Ty::Table(K)`. Outside queries a law must declare the table in its signature (typed E108).
- A write to a table row is already E501 (writes outside the owned set).

### 2.2 Motion modules (`loft-passes/src/motion.rs`)

Per kind K (as today) the scheduled laws and checks of K fuse into one module. New: the module
collects `reads` = the table parameters of K's laws/checks in first-use order.

- `reads` empty: the existing text, byte for byte (the Load gate compares module text).
- For S ≠ K: `@group(1) @binding(4 + j) var<storage, read> loft_rows_S`, a `struct Row_S` and
  `fn loft_read_S(i: u32) -> Row_S`, generated by the same code that writes `struct Row`.
- For S = K (a law reads other rows of the kind it writes): `@group(2) @binding(3)
  var<storage, read_write> loft_prev`, `loft_read_K` loads from it, and a second entry
  `snapshot` copies `rows` to `loft_prev`. This is the second buffer of the rule; a law that only
  reads other kinds gets none.
- WGSL cannot pass storage arrays by value, so a table parameter is erased from every WGSL
  signature and call; `legs[i]` lowers to `loft_read_Leg(u32(i))` wherever it appears.
- A helper's `Row` type for another kind lowers to `Row_S`.

### 2.3 Hazard order, derived and checked

Dispatch position of K = schedule position of K's first law (checks count after laws). A
dispatch is *lockstep* if it reads a kind that has a dispatch, is read by one, or reads itself.
Lockstep dispatches run one tick at a time, in position order; the rest keep today's fused
multi-tick dispatch unchanged.

For a reader R (a law or check of K, schedule position r) of S ≠ K the rule asks for:
`before = ∃ S-law at position < r`. The dispatch order delivers: `S dispatched before K`.
The compiler requires `before == (S before K)` and, when `before`, that every S-law is before
r. Otherwise E505 "laws of S are scheduled on both sides of R". For S = K the rule asks for the
previous tick, which the snapshot delivers. Data kinds (no laws) are constant: any order is right.

### 2.4 Program and bundles

- `Dispatch` gains `reads: Vec<DispatchRead { kind, input, previous }>` and `lockstep: bool`
  (serde-defaulted, skipped when empty, so existing artifacts and bundle hashes are unchanged).
  `DispatchResource` gains `Read(j)` and `Previous`.
- A read binds the read kind's live table: its dispatch's rows if it has a dispatch, else the
  drawn kind's rows, else a static table of its packed words.
- Lockstep group = one `PassLoop { cond_buf: None }` whose body is the group's tick passes
  (`snapshot`, `advance` per kind). The IR schema does not change; the meaning is new: a loop of
  tick passes advances its body one tick per iteration until caught up.
- Runner (`loft-wgpu` Linker → `Order::Lockstep(ids)`; `loft-runner` encode): for each due tick,
  each pass in order advances to that tick. Timed advances stamp the group's first and last
  dispatch.
- `sample_motion` (stills, clips, trace-check) loads one bundle for the lockstep group and reads
  back each kind's rows; row-local dispatches keep their own bundles.

### 2.5 Kind queries

`KindTable.reads` lists the drawn kinds a kind's queries read. Each read binds at
`@group(1) @binding(4 + j)` in that kind's module; vis, shadow and shade passes bind it to the
read kind's row table. The tiled World and path tracer compile every kind into one module and
do not get this binding: a kind that reads rows there is E405.

### 2.6 The twin

The trace twin (`loft-verify trace-check`, TWIN-signed logs) runs laws on `Eval` law by law in
schedule order, mutating the tables in place, which is already the rule for other kinds. Table
parameters bind as views (`Eval::views`: name → kind index), and `legs[i]` is `Val::Row`. A law
reading its own kind gets a snapshot of the table taken before K's first law of the tick.
`Eval` also resolves `K[i]` in queries, so bound derivation of a trace that reads another kind
works. New recordings are GPU-signed (record and replay both run `sample_motion`), so they agree
if the lockstep path is deterministic, which it is: every read is of a fixed version.

## 3. Library

`stdlib/motion/legs.loft` (new): `Trunk` (drawn: the existing torso, claws and eyes SDF, no legs)
and `Leg` (drawn: two analytic capsules and a toe ball, all three points written by the leg law in
World space, so the query is closed form and per-leg bounded). `trunk_plan` emits the legs then
the trunk. Gait helpers that take no `Walker` (`hull`, `contact`, `hold`, …) are imported from
`gait.loft`; the ones that read `Walker` lanes are rewritten over gathered lanes.

Split of the multi-swing gait:

| `step` (fat row) did | now |
|---|---|
| trunk state, wanted CoP, capture, spill, head, lean, phase per site, lifter choice with the veto, leash | `stride` (Trunk), reading legs as the previous tick left them |
| per-site swing state (anchor, age, clock, span, aim) | `swing` (Leg), reading the trunk `stride` just wrote (`lifter`, centre, yaw, lean, start velocity, spill, urgency) |
| hull of the new pins after landings | `stride` next tick: recomputed when the aloft mask changed (same value one tick later in the computation, the same tick in effect) |
| `present`: toe pose | `swing`, plus hip and knee (IK once per tick instead of per march step) |

Known differences from the fat row: `support_kind` and `cop_margin` are of the hull at tick
start (the fat row reported the hull after this tick's landings). `steps` counts a landing one
tick later. Neither feeds back into motion.

## 4. Predictions

**Dispatches.** Two lockstep dispatches per tick (stride, swing), no snapshot. 60 fps at 120 Hz:
4 per frame (crab_live: 1 per frame).

**P3, motion cost.** `stride` is the old `step` on one thread minus the leg loop (the gather of
8 rows adds ~100 loads); `swing` is 8 threads of the old leg loop plus pose plus one IK. On the
M4 a one-thread dispatch of this size is ~10–20 µs, a dependent dispatch adds ~5 µs of gap.
Per tick ≈ 20–30 µs, per frame ≈ 0.04–0.06 ms. Predicted 0.05 ms per frame, under the 0.15 ms
bound. Instrument: `sample_motion_timed` (first dispatch start to last dispatch end) over a
catch-up of 0..t; per frame = total / (60 t).

**P2, frame time.** crab_live today: 10.8–11.6 ms quiet, 14.5–15.4 ms p50 at load ~9.5 (stride
note). The trunk SDF loses eight IK legs per evaluation (each ~2 capsules + a sphere + IK ≈ 4× the
cost of the trunk alone) and its proxy box shrinks from the leg span (≈1.5 m × 1.4 m) to the trunk
and claws (≈1.3 m × 0.8 m), so trunk march cost drops to ≈ 20% of today. Legs: 8 analytic
proxies, each a ≈0.7 m box, closed form, ≈ 0.4 ms for vis + shadow + shade. Floor (deck, classify,
present, shadow raster of the deck) ≈ 2 ms. Predicted crab_rows ≈ 0.2 × 9 + 0.4 + 2 ≈ 4.2 ms p50,
p95 ≈ 4.6 ms quiet: P2 holds with a thin margin. Under the usual load (~9) predicted ratio
crab_rows / crab_live ≈ 0.35–0.4 on the same binary, since contention scales both.

**Rust lines.** Checker +15, motion lowering +150, bundle +90, runner +50, twin +40, eval +20:
≈ +370 net. The design predicted "the kernel should not grow much"; 370 lines is the price of
capability R without removing any pass (P5's reduction comes with Probe A).
