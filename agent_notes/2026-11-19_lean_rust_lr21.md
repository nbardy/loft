## What

`rust/crates/loft-core/src/{rate,kernel,schedule,layout}.rs`: 524 scc code lines (ceiling 1,000).

- `rate.rs`: `Rate { frame, item }`, which records two bits rather than TS's rank `build < frame < copy < item`. A
  Map body that reads its row index and a param is per item for lifting, but per frame for classification. One rank
  cannot say both. Binders owned by a `Fn`/`Loop` decl are neutral, and a program's own binders are `item`. The pass
  is one forward pass in node order. `frontier` is TS's lift rule (`LIFT_MIN` 3, the same op costs).
- `kernel.rs`: `Source` (`Made(Shape)` | `Curve`), `Decl { writes, fill, when }` and
  `Fill { Map | Scan | Raw }`. `plan` classifies each decl once, as the plan rules require:
  - A Const Map or Scan is run on the f32 tape at compile and becomes `Init::Bytes`.
  - A Const body that the tape cannot run yet (fetch, loop, raw, `pick`) becomes `When::Load`.
  - A per-frame body stays `Frame`, and its per-frame frontier is lifted into frame-values resources by read depth.
  - `Steps` and `Raw` keep the clock they declare.
  - `kept(&When)` counts the states of a `Steps` resource: from the step at time max(from, 0), then every k steps.
    The host replays between them.
- `schedule.rs`: `levels` gives each kernel a level within its phase. A read into a later phase is a typed `Scene`
  refusal, and so is a cycle. `schedule` puts Load, then Steps, then Frame, each by level. Map, Scan and frame-values
  kernels of one level make one dispatch. A raw pass or a stepped kernel is its own dispatch.
- `layout.rs`: packs row resources first fit into storage buffers, with written and read-only resources kept apart.
  The limits are 5 buffers and 128 MiB per binding, and exceeding either is a typed refusal. A stepped resource holds
  every state it keeps.

Check input: the recorder does not yet write Kernel bodies, and the wire does not yet decode lane 1.2's jobs (see the
wave 1 note in `lr12.md`). So `rust/crates/loft-core/dump_kernels.ts` (118 lines) walks the TS objects instead, as
`dump_math.ts` does for lane 1.3. For each scene it writes:
- the TS plan: tables, stages, recurrences and compute passes;
- the authored kernels as graphs: map runs, scans, recurrence start and step, and compute;
- TS rest fills.

`tests/it/kernels.rs` builds `loft_ir::Graph` from that output.

## Pass / fail (M4, `tools/dev.sh test loft-core --release --no-capture -E 'test(kernels) | test(const_fills)'`)

Fixture: `bun rust/crates/loft-core/dump_kernels.ts > out/lr21/kernels.jsonl`. It takes 2 min 40 s at nice 15 and
writes 70 MB. Of 125 files, 71 scenes build; the rest are library files or the known refusals.

| Check | Result |
|---|---|
| Every TS table, recurrence and compute output has a resource with the same rows and lanes | **PASS**: 4,008 tables, 0 misses. 19 opaque `prepare` fills (lane 2.4) are stood in for and counted. TS's 102 frame-values tables and 2 replay tables are lowering or host products; they are not authored |
| `Steps` keep the same history | **PASS**: 10/10. Rope keeps 1,921 states, flock 901, creep 57 (checkpoints of 16), skin 1, compute_steps 31 |
| Per-frame dispatches ≤ TS | **PASS**: no scene over. 207 in total against TS's 445. 161 Const fills that TS dispatched every frame now run at compile |
| Const fills equal TS's f32 fills within 1 ulp | **FAIL as written**: 160 compile fills compared (17,900 values). 81 are within 1 ulp and 79 are not (822 values, 4.6%). Worst \|got − want\| / max(1, \|want\|) = **9.2e-6**. Every miss is cancellation in an f32 evaluation against TS's f64-then-round. Examples: `body_*_spine` transported frames (scans of cross and normalize); pool's arch spine, where f32 gives −2.1e-7 and f64 gives 2.9e-16 for an exact 0 |

Other measurements:
- 4,143 values lifted from kernels. TS's 11,194 frame-values lanes also include lifts from draws, which are lane 3.1's.
- 5 kernels became `Load`: 2 author load passes and 3 Const bodies that read a fetch or a loop.
- `plan` + `schedule` + `layout` over all 71 scenes take 0.40–0.50 s in release, including Titan.
- `tools/dev.sh lint loft-core` (gate flags, `wildcard_enum_match_arm`) is clean.

**Why the fill check fails.** Plan §3.4 moves the table fills to the f32 tape with `libm`. A body that cancels
cannot then stay within 1 ulp of an f64 evaluation rounded once. Lane 1.3 measured the same thing: `op:dot` 152 ulps,
`expr.test#3` 202 ulps, all within 1e-6 relative. The GPU stage that TS ran for these same tables every frame was
also f32, so its pixels already carried this difference. The owner must choose between two changes:
1. Re-score the check as a relative tolerance against TS. The worst value measured is 9.2e-6, which is inside
   `Tol::f32_rel(1e-4)`, the margin tolerance §2.2(b) uses.
2. Compare against TS's GPU stage output, which needs a GPU run (lane 3.2's corpus).

I did not move the gate. `const_fills_within_1_ulp_of_ts` asserts the gate as written and is red. The structural test
`kernels_account_for_the_ts_plan` is green.

## Integrator notes (one-line registrations, not committed)

- `rust/crates/loft-core/src/lib.rs`: `pub mod kernel; pub mod layout; pub mod rate; pub mod schedule;`
- `rust/crates/loft-core/Cargo.toml` `[dependencies]`: `loft-ir = { path = "../loft-ir" }`. `rust/Cargo.lock` gains
  `"loft-ir"` in loft-core's dependency list (`cargo update -p loft-core --offline`).
- Committed: `tests/it/main.rs` gains `mod kernels;`, which compiles once lib.rs has the modules above.
- The decoder of `Kernel` decls (the wire owner's job) produces `kernel::{Source, Decl, Fill}`:
  - a table maps to `Source::Made(Rows)`;
  - a curve row maps to `Source::Curve`;
  - a map run, scan, recurrence start/step and compute pass map to a `Decl`;
  - a recurrence start has `When::Load`;
  - a table or map has `When::Frame`, meaning at most per frame.

  `Fill::Map.f` is a `Fn` decl `[i, lanes...]`. `Fill::Scan` takes an `init` `Fn` `[]→state` and a `step` `Fn`
  `[state..., i]→[next..., lanes...]`.
- `kernel.rs` has a private `twin(loft_ir::Prim) -> loft_core::prim::Prim`, because the two enums list the same
  operators in different orders. Delete it when the wire reconciliation unifies them.

## Left

- The planner is checked through the TS bridge, not through recorded jobs. When the recorder writes Kernel bodies,
  the same test should take decoded jobs. `dump_kernels.ts` is then deleted.
- The tape cannot run `Fetch`, `Loop` or `Pick` yet. Const bodies with them are `Load` (3 in the corpus). Adding a
  gather instruction to `tape.rs` would move them to compile.
- TS also lifts per-frame values shared by two or more single-entry programs (`readers >= 2`). That rule is not
  ported here; it is emit's (2.2) and draws' (3.1), with the same `frontier`.
- Replay dispatches for checkpointed `Steps` are the host's (3.2). The corpus has 2 TS replay tables, counted in TS's
  dispatches.
- The 1-ulp fill check: the owner's call (above).
