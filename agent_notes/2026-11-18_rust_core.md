# Rust compiler core, 18 Nov 2026

Branch `feat/rust-core`. Follows [the compiler-speed proposal](../docs/proposals/2026-11-18_compiler_speed.md) and
[its measurements](2026-11-18_rustplan/NOTE.md). `LOFT_CORE=rust` routes two kernels through a Rust library:
`solve`'s numeric rounds and its verification, and the shader sharing in `host/share.ts`. The TypeScript compiler is
still the default and is unchanged. On every example that builds today, the Rust path writes byte-identical
artefacts. Only the solve-heavy scene meets its target. The other targets are out of reach with this design,
for the measured reasons in "Why the targets were missed".

## Results

`timing.ts` (beside this note) ran 3 alternating rounds per scene, `loft build`, `LOFT_NO_GPU=1`. Figures are
medians of whole-process CPU (user + system), wall time and peak RSS. The machine was shared, with 1-minute load
14–15, so treat these as observed values only.

| Scene | TS CPU / wall / RSS | Rust CPU / wall / RSS | Target (CPU) |
|---|---:|---:|---:|
| Owl | 315 ms / 128 ms / 156 MiB | 286 ms / 123 ms / 152 MiB | ≤ 50 ms |
| Titan | 2128 / 924 / 570 | 1475 / 791 / 492 | ≤ 150 ms |
| Thin film | 216 / 106 / 116 | 211 / 100 / 111 | — |
| Storm (exit 4 both) | 765 / 310 / 267 | 718 / 290 / 251 | — |
| Heron leap | 2274 / 1227 / 1106 | **791 / 325 / 236** | ≤ 250 ms |

Peak RSS is 4.7× lower on heron. It barely moves elsewhere (target: ≥ 3×).

The kernels alone, same inputs:

| Kernel | TypeScript | Rust |
|---|---:|---:|
| heron `solve()` call, base variant (rounds, verification, and the JS setup they still need) | 874–1674 ms (varies with load) | 113–141 ms |
| the solve kernel itself (`loft-core-replay`, fastest of 20) | — | 58 ms |
| Titan `share()` in-process, warm | 90 ms | 45 ms (28 ms kernel, the rest packing) |
| Titan `lower` line of `loft build`, cold | 149 ms | 54 ms |

The heron target (solve ≤ 100 ms) is missed by about 20 ms. Of the call, 58 ms is the kernel. The rest is
symbolic derivatives and packing, which stay in JS.

## Parity

- **Corpus** (`corpus.ts`): all 124 `examples/**/*.ts` were built on both cores. The 63 that build have the same
  SHA-256 over the manifest, `bin/` and `wgsl/`. The 61 that do not build give the same exit code (52× 3, 4× 6,
  4× 4, 1× 1) and the same verdict line. No refusals occurred.
- **Solve report**: heron base and `moved` agree on steps (309, 402), rounds (4, 4), samples (394, 390) and every
  hold's worst value and time.
- **Math**: the tape uses the platform libm, as JSC does. 400,000 random inputs each to sin, cos, tan, exp, log,
  sqrt, asin, acos, atan, sinh, cosh, tanh, log2, pow and atan2 give the same bits as Bun. One trap: LLVM rewrites
  `pow(2, y)` as `exp2(y)`, which differs in the last bit (766 of 400k). `jsmath::pow` hides its operands from
  LLVM, and JSC's square-and-multiply path for nonnegative int32 exponents is copied.
- **Focused tests**: `tests/solve.test.ts` and `tests/files.test.ts` pass 19/19 on TS. With the Rust kernels
  preloaded (`LOFT_CORE=rust bun test --preload ./src/core/native.ts …`), 18/19 pass, including the solve error
  cases (infeasible, unsolved, unreadable). The failing test spawns a child Bun without the preload. The child
  correctly prints its named refusal on stderr, and the test expects stderr to be empty.
- Checks: `cargo build --release` and `pnpm typecheck` are clean. The full suite was not run (integrator's).

## Design

**Boundary.** `rust/loft-core` is a cdylib with no dependencies, loaded through `bun:ffi` by `src/core/ffi.ts`.
Each job makes two calls: `loft_core_call(kernel, bytes)` runs the kernel and keeps the result, and
`loft_core_take(out)` copies it out. One packed buffer goes each way, so the call cost does not matter. I chose
bun:ffi over wasm because wasm ships its own libm, and bit parity with the JS twin depends on the platform's.
Loading costs about 7 ms CPU per process: dlopen plus Bun's trampolines. The first status byte is one of: ok, a
typed failure (the kernel's own payload), a malformed input (a packer bug, thrown) or a caught panic (thrown).
`LOFT_CORE_DUMP=dir` saves every input. `loft-core-replay <kernel> <file> [n]` times one input in isolation.

**Switch.** `src/core/switch.ts` imports nothing Bun-only, because the browser host imports `share.ts`. It reads
`LOFT_CORE`, which must be unset, `ts` or `rust` (any other value throws). `src/cli/main.ts` imports
`src/core/native.ts` under `rust`, and that import registers the kernels. A kernel goes back to TypeScript only
through `refuse(kernel, reason)`, which prints `loft core: <kernel> stays on TypeScript: <reason>` once per reason
and records it in `refusals`. Refusals are:
- the core is not loaded in this entry point (tests, tools, child processes);
- a hold reads a library function (its CPU twin is JS), a table, a loop, or a variable the kernel does not set;
- the share kernel's own refusals (below).

A missing or stale library is an `EnvironmentError`, never a silent fallback.

**Tape (`tape.rs`, packed by `src/core/tape_pack.ts`).** Expressions travel as data: the nodes the roots reach,
dependencies first, one numeric record each. Leaves are resolved once in JS: a variable becomes a slot, `time`
becomes the clock, and an input or param becomes the value compileJs would read. Compilation does what compileJs
does while it writes JS:
- each vector becomes one value per component;
- a component is known now or a register;
- known operands fold with the same function;
- the identities x·0, x·1, x+0, x−0 and x/1 apply to known operands;
- a known −0 written as an operand becomes 0, because `jsLit` prints `String(-0)` as `"0"`.

Run time is one linear pass. Every register holds a lane per evaluation point (`regs[r·lanes + l]`), and literals
sit in registers, so every operation is a tight loop over registers. All samples of a hold run as one batch.
Because evaluation is pure, checking the lanes in order afterwards raises the same first error JS raises.

**Solve (`solve.rs`).** This is a line-for-line twin of `Problem` (rows, descend, augmented), `diagnose`, `peaks`,
the exchange rounds, and the verification of the returned f32 curves. It does the same f64 operations in the same
order. The structural conflict certificate is computed in JS from the hold's shape and passed as data. Failures
come back typed and are thrown as the same `SolveError`. Speed comes only from places where the order of
arithmetic is unchanged:
- batched lanes;
- jets computed only for the slots a tape reads;
- B-spline weights shared per channel shape;
- gradients stored on the touched entries only (`addRow` reads no others);
- Cholesky factoring four rows together, each entry still the JS subtraction chain;
- reused buffers.

**Stays in JS for solve:**
- classifying holds and calling the author's `hold` callback;
- symbolic derivatives (`grad.ts`);
- the preference quadratic and the start;
- the cache;
- building the returned bsplines.

**Share (`share.rs`).** This is a twin of `host/share.ts`. Each JS regular expression is written out as a scanner
that makes the same choice: leftmost, first alternative, greedy with backtracking where the pattern needs it. The
twin reproduces the tokens, keys, holes, row dedup (`JSON.stringify` equality) and the plumbed group WGSL. It
refuses a whole artefact in three cases:
- non-ASCII outside a comment, where JS `\s` would differ;
- a `$` in shader text, which `String.replace` would read as a pattern;
- a template missing a line that `plumb` edits.

- `src/cli/main.ts`: +2 lines in `main()`, importing `../core/native.ts` when `LOFT_CORE=rust`.
- `src/host/share.ts`: +1 import and +3 lines at the top of `share()` (dispatch).
- `src/geom/solve.ts`:
  - imports `rustKernel` and the `NativeSolve` type;
  - `Line.roots` (`withGrad`'s roots) and its one assignment;
  - `checkedEvaluator` compiles on first use when the roots hold no library function. compileJs can fail only on
    a library function, so the outcome is unchanged, and the Rust path never pays the compile (about 30 ms per
    heron solve).
  - Two dispatch points: `native?.rounds(…)` before the rounds loop (`else for (;;)`), and `native?.verify(…)`
    with the existing measurement wrapped in `?? (() => { … })()`.

Everything else is new: `src/core/*` and `rust/loft-core/*`.

## Why the targets were missed

The targets assumed most of a build was graph→artefact work that a native backend could absorb. Profiles of the
Rust-path build say otherwise. Main-thread samples, `bun --cpu-prof`:

- **Titan (≈1.4 s sampled).**
  - `compileScene` takes 53%. Of that, drawables' `draws` take 40%: author surface callbacks, and `gridDetail`
    instantiating each surface's graph at 25 constant rest points (27% by itself).
  - Table `declare`/`classify` takes 13%. These run `map`/`scan` callbacks that build nodes.
  - compileJs for CPU fills and the rest measurement takes 9%.
  - Module evaluation (library plus scene top level) takes about 25%. `lower` and `write` are now about 6%.

  Whole-process CPU is also well above main-thread time: JIT and GC threads.
- **Owl (≈210 ms sampled).** Import plus parse takes about 35%. `compileScene` (graph and draw callbacks) takes about 27%.
- **Floor.** Bare Bun is 10 ms CPU. Importing `src/index.ts` from source is 70–80 ms CPU.

Graph construction runs author code: styles, drawables, `map`/`scan` bodies and `iterate` steps. Those callbacks
stay in JS by design, and they alone exceed the Owl and Titan targets. Moving all of fold, plan, lower, emit and
table layout to Rust would remove at most about a third of Titan's main-thread time.

**Library precompile (target 3) is blocked on exactness.** These were measured:

- A CJS bytecode bundle of the library imports in 10–20 ms CPU, against 70–80 ms from source. Pre-transpiling
  per file through a plugin gains nothing, because the cost is module linking and parse, not transpilation.
- ESM bytecode needs `--compile`, and CJS cannot hold the modules with top-level await (`main.ts`).
- The scene's own imports must be mapped onto the bundle's module instances, which needs a runtime plugin.
- The blocker: expression IDs come from creation order and appear in emitted WGSL. Evaluating the library from a
  bundle changes when library modules run relative to the scene's modules, so node IDs, and therefore bytes, can
  change. It also changes stack frames, which `siteOf` reads.

## Next steps, by expected payoff

1. **WGSL names independent of creation order.** Renumber canonically by first use within each emitted module
   (expr.ts emit). This unlocks the bytecode library bundle (about 55 ms CPU per job measured headroom) and warm
   workers. It is a format-visible change: every WGSL byte moves once.
2. **Rest measurement without 25 graph instantiations per surface.** Evaluate one symbolic surface at the 25
   points in the tape (lanes). It needs a check that the values match the constant-folded instantiations bit for
   bit, or a recorded change. This is the largest single Titan item (about 27% of main-thread time).
3. **Tape support for `fetch`, curve rows by slot, and `iterate`.** Then CPU table fills (`cpuFill` map/scan) and
   the rest frame can run as batched lanes, with JS pre-reading fetched tables in compileJs's order. This removes
   compileJs and its JIT from the build (9% of Titan main thread, plus RSS).
4. **A backend port (fold, rates, lower, emit, layout) over an arena exported after `draws`.** The proposal's
   3–6 week line. It is worth doing after 1–3, once those have removed the callback-bound work it cannot touch.
5. **Smaller items:**
   - an N-API addon instead of bun:ffi (about 7 ms load per process);
   - interning identifiers in `share.rs` (28 → about 8 ms on Titan);
   - the remaining solve gap: derivatives in JS (about 18 ms per solve) and kernel interpretation (about 13 ms).

## Reproduce

```sh
cd rust/loft-core && cargo build --release && cd ../..
LOFT_NO_GPU=1 LOFT_CORE=rust bun src/cli/main.ts build examples/second/heron_leap.ts --out out/x
bun agent_notes/2026-11-18_rust_core/corpus.ts        # parity over examples/**/*.ts (both cores)
bun agent_notes/2026-11-18_rust_core/timing.ts 3      # the table above
LOFT_CORE_DUMP=out/dump LOFT_CORE=rust bun src/cli/main.ts build … && rust/loft-core/target/release/loft-core-replay 1 out/dump/1-0.bin 20
```
