## 1. Particle-to-grid transfer for GPU physics

Give an author a grid table and a `kernel … allow(atomics)` that evaluates a stencil and deposits mass and signed momentum. Use a separate pass to normalize nodes with positive mass, apply grid forces or solve pressure, then gather velocities back to particles. FLIP retains the pre-solve velocity for its grid delta. The trilinear FLIP example has eight destinations per particle. Quadratic 3D MLS-MPM has 27 and adds an affine/stress term to momentum. Bound that term too. SPH commonly gathers from a neighbour list. Its grid density splats or pair-force scatters can reuse the same accumulator, with kernel support or neighbour count supplying the bound. These are library choices. A barrier between workgroups inside a dispatch cannot implement the transfer/solve boundary. [Kernel and effect contract](../spec/PATCH_V1_2.md)

**Tier A · Exact fixed-point accumulation.** Use an unsigned mass accumulator and signed component accumulators, or signed words for all four when the mass bound fits. Choose a power-of-two scale S per physical channel. Deposit the integer nearest to S times each contribution, with a specified tie rule. The CPU and GPU must agree on the cell, weights, integer multiply/divide widths, rounding and boundary policy. Emitters can use quantized coordinates and integer weights, as in the probe. Unconstrained floating arithmetic up to the final cast cannot promise identical inputs. Discard the old value returned by each add. Read the completed grid in a later pass. Then associativity and commutativity give the same words for every interleaving.

Let K bound contributions to one node in a tick and A bound the absolute magnitude of one contribution in that channel's units. Require `K × floor(S × A + 0.5) ≤ 2³¹−1` for signed channels or `≤ 2³²−1` for nonnegative mass. This protects every partial sum even under cancellation. Quantization is at most `1/(2S)` per contribution and `K/(2S)` per cell in physical units. For example, 1,024 contributions of at most 2 kg·m/s with S = 2¹⁹ fit in i32 (1,073,741,824 counts), with at most 0.000977 kg·m/s total rounding error. If conservation must hold **after** quantization, quantize the particle total once and assign the signed residual to a deterministic stencil entry. Budget that entry separately.

Use the global particle count as K if it fits. For tighter ranges, count occupants of the supporting cells before deposit. Validate finite inputs, intermediate products, scales and bounds in wide arithmetic. If precision and range cannot both fit, split into bounded integer partials and reduce into a wider pair of words, or reject the step with the offending cell/channel. Publish the grid only on success. Wrap, saturating adds and a late overflow check on the final signed sum can each produce a plausible, wrong grid. Pin the scale, retry policy and initial state in replay. The CPU twin computes the same quantized contributions, sums in i64, checks representability and compares every word at the pass boundary. Exactness of a full solver also requires exact G2P, grid solve and time integration.

**Tier B · Race-tolerant f32 accumulation.** Request `wgpu::Features::SHADER_FLOAT32_ATOMIC` and emit `atomicAdd` on `atomic<f32>` storage. The pinned HAL grants this on Metal with MSL ≥3.0 and its float-atomics family test (Metal3, Apple7 or Mac2), and on Vulkan with the buffer f32 atomic and add capabilities of `VK_EXT_shader_atomic_float`. The M4 granted it and executed the shader. Add one device capability to Loft's link selection for an authored float-atomic variant. The existing type checker already records integer table writes as Det and float atomic writes as NonDet. Carry that provenance through aliases, later passes, checks and exact state. Diagnose E504 at an exact consumer with the producing source span. Ordinary consumers run. Keep kernel effect permissions and memory validation active in both modes. A `wgsl det` assertion cannot certify float accumulation. Source kernel lowering and the current row-local CPU interpreter still need work for this cross-row case. [Checker](../../crates/loft-passes/src/check.rs) · [Compute twin](../../crates/loft-std/src/compute_twin.rs) · [Pinned feature](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-types/src/features.rs#L611-L620) · [Metal selection](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/metal/adapter.rs#L1279-L1282)

For the statistical twin, pair the same particles, seeds and boundary conditions with an independent f64 CPU transfer. Reject nonfinite values. Compare total mass and each signed momentum error normalized by the sum of absolute input contributions so cancellation cannot hide a miss. Score cell RMS and maximum error, then drift in mass, energy and velocity distribution over a fixed number of solver steps. For this unit-mass fixture, set relative global error ≤10⁻⁵, absolute per-word maximum ≤10⁻⁴ in physical units, across 32 seeds including clumps and reversed particle order. For a full simulation, set physical tolerances per fixture and require the 95% interval of the paired ensemble difference to fit those tolerances. Energy uses the expected work/dissipation of that solver. The four readbacks below establish a one-step observation only.

**Browser fallback.** Core WGSL already supports integer atomic adds. Keep Tier A on the web when scale and occupancy permit it. For floating transfer without native f32 atomics, stably radix-sort `(baseCell, particleId)` in initial ID order, build start/end ranges, and let each destination gather from its eight or 27 incident ranges. Specify the neighbour order and the reduction tree, including any partials for long cells. This is scatter by sorting with one final writer per destination. It also serves exact scenes using integer or strictly specified arithmetic. Ordering alone does not make ordinary f32 arithmetic bit-identical across devices. For 65,536 particles on a 32³ grid, two 8-byte key/ID arrays cost 1 MiB and ranges cost 256 KiB, plus radix histograms/scan scratch. Two 8-bit digit passes cover the 15-bit base-cell key. Predict **2–6 ms** including bins, ranges and gather on M4 browser WebGPU, subject to measurement. The cheapest browser test forces this route on the same inputs, reads the grid and times the entire pass list. [WGSL atomic types](https://www.w3.org/TR/WGSL/#atomic-types)

**Measured P2G.** One invocation per particle, 64 per workgroup, 65,536 unit-mass particles, periodic 32³ grid, eight CIC splats, four 32-bit adds per splat. Each launch issues 524,288 node contributions and 2,097,152 scalar adds. Positions have four fractional bits per axis. The exact weight numerator W is the product of the three tent factors (0…16), over 4,096. Velocity components v/63 use integers v in −63…63. Fixed words use W for mass and nearest(Wv/63) for momentum. The global magnitude bound is 65,536 × 4,096 = 2²⁸ per node and channel. Float uses the same positions and velocities in physical units. Spread selects all 32³ base cells. Hot selects 4³ adjacent base cells and still writes the same full grid. The 1 MiB particle buffer and 512 KiB output grid stay resident.

## 2. Data-driven materials alongside kinds

A thousand variations of wood can share one grain program. At author level, a row selects a material record containing grain scale, frequency, roughness, albedo, seed and texture indices. Geometry, pose and motion still belong to its kind. At a hit, resolve `(kind,row) → (family,materialRow)`, fetch parameters once and call the family's compiled procedural function. A bounded switch inside the family can select distinct lobe graphs. Keep eval, sample, PDF and emission consistent across direct lighting and all bounces. Use the existing typed BSDF layout and stage resolved constants. Share repeated graphs and functions across kinds. Packing 1,000 64-byte records costs 62.5 KiB. [Material layout](../../crates/loft-passes/src/material_shape.rs) · [BSDF and World interfaces](../spec/06_ADDENDUM.md)

**Compiler rule.** At load, count distinct modules and pipelines in the *whole* proposed plan, including geometry, shadows, bakes and presentation. Intern identical code/layouts first. While either scene budget is exceeded, group compatible kinds by shading contract (lobe operations, radiance type, available hit fields, resources and texture signatures), lift varying literals into columns and compile one uber-shader and tile list per family. Prefer the merge with the largest reduction in the exceeded count for the least extra shaded work. Bound switch size, bindings and register pressure. Under budget, keep faster specializations. Report counts before/after, the merge map and the costly holdouts in `loft show --plan`. A family never changes an author's public kind or row identity.

Main's renderer rejects more than 32 primary/shadow draw kinds at E520. A thousand **material IDs** fit one drawable kind today in principle. To accept a thousand material-only authored kinds, fold geometry-identical kinds before that check, carry a reversible logical kind/row mapping for picking, laws and world queries, and classify physical draw groups/families. Where geometry differs, reuse just the shade module and keep the separate draws. If incompatible geometry, interfaces or a shader that spills make the budget unattainable, report the residual count and reason. Do not raise the limit or generate a giant switch to make the count pass. [Current draw-kind checks](../../crates/loft-passes/src/lib.rs) · [Scene budgets](../../engines/gates.json)

For unrelated textures, use Loft's `BINDLESS_TEXTURES` only when the device enabled `TEXTURE_BINDING_ARRAY` **and** `SAMPLED_TEXTURE_AND_STORAGE_BUFFER_ARRAY_NON_UNIFORM_INDEXING`, with enough elements in the requested stage limits. The M4 advertises both. Use separately bounded sampler classes, validate indices on bundle load/update and specify gradients or LOD for divergent samples. Portable fallback uses `texture_2d_array` layers with compatible size/format/mips, or atlases with mip gutters and UV transforms. Split batches/pages for incompatible samplers/formats. Include those extra pipelines, binds and draws in the budget. The software BVH remains the reference and the deployed browser route. Loft already has a software tree and refit code, a transformed-triangle loader and a WGSL mesh-ray helper. ## 4. Neural shading and cooperative matrices

A small MLP fits an ordinary WGSL material function. Put trained weights in a read-only table, unroll dot products, keep hidden activations thread-local and fuse the evaluation at the shading site. A material family ID or table offset selects the weights. No neural backend or tensor IR is required. Start with a plain ALU variant for the browser and the CPU twin. Keep the output in linear material/radiance units, with the same bounds as its analytic counterpart. Profile the integrated shader for occupancy/spills: the source can hold activations in local values, but register allocation is up to the driver.

**Measured ALU probe.** One 64-thread-workgroup kernel shaded 512 × 512 samples with f32 **8 → 16 ReLU → 3**, zero biases, 176 runtime weights (704 B), 176 MACs/sample or 46,137,344 MACs/dispatch. The unrolled first layer uses two vec4 dots per neuron. The second layer uses four per channel. Each invocation reads two varying vec4 features and writes one vec4 result. The I/O control performs those same reads and store, writing the input sum. Both ran on a device requesting timestamps and ordinary WGSL alone. Eight warmups and 64 alternating pairs used the physics timer. M4 triangle before/after was 1.501/0.931 ms.

|---|---:|---:|
| Input/output control | 0.232 | 3.221 |
| ALU network | 0.238 | 0.854 |
| Network minus I/O, paired differences | +0.012 | +0.649 |

Every RGB output (786,432 components) was finite and within **1.86×10⁻⁷** of independent f64 inference over the uploaded f32 values. ## 5. The heavy-lighting regression

**What regressed.** Section B at 1280 × 800, 20 groups of seven matte capsules, gave native **58.269/56.205 ms p95** against legacy **26.608/28.903 ms** (+31.66/+27.30 ms, 2.19×/1.94×). At one group the excess was 3.76/3.01 ms. On matched *reduced* lighting at 20 groups native was 0.54 ms faster then 0.71 ms slower. The heavy fixture uses the same sun visibility ray, one cosine-weighted diffuse bounce, pixel-indexed RNG, sky and film curve on both engines. Native issues one draw to legacy's five commands. The GPU work inside it explains why command count was misleading. Seven of eight native historical triangle controls exceeded 0.350 ms. These deltas cover the whole path. [Matched A/B results and image comparisons](../../agent_notes/2026-11-20_v1/AB_OLD_VS_NEW.md#b--legacy-lighting)

Main's single-sample Vis64 and `shade_tiles` callback cannot supply the sample coverage, hit, pixel and World needed by this transport. The authored `screen_pass` replaces raster visibility. Four software BVH queries per output pixel means **4,096,000 primary traversals/frame**, including the sky. It deduplicates hit rows only after tracing, then reconstructs the centre or first covered hit, computes six field samples for its normal, and sends shadow/bounce rays. Legacy rasterizes multisampled proxies and shades each covered row at pixel frequency. Secondary traversal, normals and output encoding also differ. The archived +27–32 ms measures all of those differences together. [Matched shader](../../engines/realtime_matched.loft) · [Native visibility pipeline](../../crates/loft-cli/src/native/mod.rs)

**Isolation probe, run.** Generate B's native scene as in `tools/ab_legacy.sh --matched`. In one scratch copy change only the coverage loop bound from four to one and the final coverage divisor from four to one. Leave sun, bounce, seed and first-tap position intact. Run four/one/one/four at count 20, t=0, using immediate timestamps, eight warmups and 60 frames each. Native four-tap/one-tap p95 was **55.716/29.305 ms** in the first pair and **51.680/27.548 ms** in the reversed pair. Dropping three taps saved 26.411 and 24.131 ms, respectively. Triangle controls in execution order were 1.492, 1.615, 0.466 and 0.735 ms. Different edge coverage also changes how many distinct rows get shaded. This supports replacing repeated primary traversal. A one-tap renderer would change the picture.

**Fix the missing interface.** Implement the existing `ShadeFn(w: World, h: Hit, wo, ink, px) → rgb` contract and make the matched recipe use it. At load, choose a supported 4× integer visibility attachment and matching depth. The M4 advertised 4× renderable/sampleable RG32Uint and Depth32Float. A browser can use the spec's RGBA16Uint encoding where its format supports the required usages. Carry per-sample ID and hit payload through classification. Load each sample by index in a later pass, preserving background and coverage. Integer IDs cannot be averaged by a resolve. Rasterize bounded proxies with conservative coverage and correct surface depth/discard per sample for analytic silhouettes. Limit costly tests to covered proxy fragments. Check actual coverage/depth against limb intersections, thin edges, centres that miss and rows that overlap before timing. Resolve each pixel's distinct (kind,row) once. Reconstruct a centre hit when available and otherwise use a covered sample and its matching position/depth. Compute analytic capsule normals where defined. Shade using the same PCG dimensions and secondary World rays, multiply each row's **linear** radiance by its covered sample count/4, add the sky share and apply the legacy film curve/sRGB once. Give each output pixel one writer, either in a fused resolve/shade pass or after a separate per-family pass that writes distinct slots. Two kind queues doing unsynchronized read/modify/write to one HDR pixel would lose mixed-edge contributions. A fully portable implementation stores the multisampled IDs between passes. On an incompatible format pick a supported encoding or the explicit four-tap software route. Native tile-memory fusion can be scored separately.

**Cost and acceptance.** Four samples need 32.77 MB visibility and 16.38 MB depth at this resolution (8+4 B/sample, decimal MB), plus ordinary single-sample HDR. A materialized visibility write + read alone accounts for up to 65.54 MB/frame of logical payload before tiling/compression. Predict **20–32 ms p95 at 20 groups** under the historical load and **9–13 ms** at one, with zero full-screen primary BVH rays. At 20, one-tap removal recovered 24–26 ms here, with one software primary still present. Raster coverage, traffic and secondary work determine whether all of the legacy gap can be recovered. First prove a single overlap tile has the right four IDs, depths, row weights and two shaded rows. Then rerun both matched schedules A and B at counts 1 and 20 for 300 frames, reverse run order, report primary/secondary counts, each pass, total p95 and cold/warm load. Require at least the archived B picture quality (47.26/37.04 dB, respectively), consistent depth/IDs away from ties, and legacy-or-better p95 on paired quiet runs. For acceptance use the v1.5 quiet-control budget and the upper 95% confidence bound on the paired native-minus-legacy delta.
