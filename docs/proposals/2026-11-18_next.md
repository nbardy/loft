# Loft next: design and plan (18 Nov 2026)

What Loft becomes after the 10–16 Nov build, the restart review (`~/git/_designs/2026-11-18_loft_restart/`: five
Claude proposals, ten Codex designs, a blind judge, two branching rounds) and the measurements of 16–18 Nov. The
review's answer was to keep Loft and add to it. Sections marked **GATED** wait on a measurement now running.

## 1. What Loft is for

Models write animated 3D scenes: creatures and bosses for the game (Keel), and samples in a training environment
that rewards models for writing them. Three things must hold:

1. **The model writes the code.** The scene is an arbitrary compute graph: any maths, any algorithm the model can
   write. Libraries exist to save tokens on standard things, never to fence the model in. A library function is a
   shortcut to graph nodes the model could have written itself.
2. **The picture is the point.** The training reward is mainly aesthetic, judged on rendered frames. Ranged checks
   and `solve` are tools the author uses (to make a leap land, to prove a jaw clears a wall), not the reward. So the
   priorities are throughput, the breadth of what the model may write *inside the training sandbox*, and the range
   and quality of looks. (Owner, 18 Nov; the plan review of the same day assumed checks were rewards.)
3. **Samples are cheap and fail only when the scene is wrong.** Deterministic, isolated, on Linux, with errors that
   name the fix.

## 2. What stays (the parts that worked)

- A scene is a module: `export default scene({ ground, things, style, sun, cameras })`.
- Shape, motion and paint are expressions in one graph (`src/expr.ts`), with two backends: WGSL (GPU) and JS (the CPU
  twin used by checks). Time is an argument; any frame draws alone.
- State is explicit (`recur`), never hidden. The one hidden state (level-of-detail memory) is gone from headless
  frames (b5cd367); only the interactive viewer keeps it.
- Typed errors with exit codes that say whose fault a failure is; `loft context`, generated from the source.
- `loft serve`: one warm process owns the GPU; untrusted compile runs in a GPU-less child; `--confine` and `--check`
  hooks (b5cd367). Creative trains through it (`creative` branch `loft/vendor-submodule`, 7c9c6963).
- Escape hatches stay: `draw.traced`, `march`, `draw.mesh`, a style written in the scene, raw WGSL.

## 3. Systems design

```
scene.ts ──▶ expression graph ──┬──▶ JS twin ─────────────▶ checks (point and ranged), solve, CPU queries
 (model)     (interned, pure)   │
                                ├──▶ bytecode ──▶ fixed interpreter shaders   TIER I: training, previews   (GATED)
                                │
                                └──▶ WGSL ──────▶ driver compile               TIER C: game, raw-WGSL scenes, hot scenes
```

**One graph, two ways to run it.** The interpreter is a speed tier, not a language. Rule: every graph the compiler
accepts, the interpreter runs or hands to tier C with a named reason (`tier: compiled, because: raw WGSL in style`);
a scene is never refused for being too clever. Bounded loops, branches, the model's own functions, tables, space
folding and `march` over the model's own field are all graph and all interpreted.

**Why two tiers, and why tier I is gated.** Measured on macOS/Metal (`agent_notes/2026-11-18_loft_serve.md`, creative
`RESOURCES.md`, probe be17739): shader and pipeline work was 83% of per-program CPU with a cold Metal cache and at
most 41% with a warm one. A whole creature's modules and pipelines cost 3.3–5.4 s cold and 0.31–0.57 s warm. The
compile child (Bun start, import, graph, lower) costs 0.45–0.85 s wall and 1–1.5 CPU s, and tier I does not remove
it. Interpreted paint costs 65–123 ps per pixel-op (2–5.5 ms per 512² stage); a 128-step march at that price costs
about 2.2 ms per field op per frame, so a folded field of 15–100 ops is 33–410 ms a frame, slower than compiling.
Nothing has been measured on Vulkan. Tier I is funded only if the Linux baseline (step 6) shows shader work at least
60% of per-program CPU in steady state and a whole-scene probe shows at least 2× completed samples per GPU-hour.
`march` goes to tier C by default, with the reason named. In training the tier is chosen once per sample and recorded;
promotion to tier C happens only in the game. (Plan review, `agent_notes/2026-11-18_plan_review/CONSOLIDATED.md`.)

**Batching.** `loft serve` accepts many tier-I scenes per submission (one bytecode buffer, an offset per scene), so
throughput is not bounded by one scene's work.

**Determinism.** A frame is a function of (scene, camera, time, size, params, inputs, tier, precision, library commit, adapter,
driver). Same tuple: byte-identical; every `loft serve` answer carries its `tier` and successful answers record precision. Across vendors: the twin and the GPU
agree within stated tolerances (section 6.5).

**Linux.** Dawn runs on Vulkan; `loft serve` is the unit a training farm runs, one per GPU. First Linux run is part of
the plan (section 8), with the staging list from creative `RESULT.md` (bun version, lockfile, bun-webgpu patch,
`bun-types@1.4.4` tarball for offline installs).

## 4. Looks: paint channels, PBR and styles

**Paint stays a colour plus optional named channels with defaults** (`ctx.channel(word, default)`). Words today:
`gloss`, `metal`, `emits`, and any word the author invents. Added: `rough` (default 0.5) and `normal` (a bump: the
gradient of a height expression, via `grad`). A scene that gives only a colour renders in every style.

**`pbr` is a style, chosen per render like any other** (`--style pbr`, `--style toon`). It is GGX with Smith
visibility and Schlick Fresnel for the sun and each lamp (with lamp shadows, as now), environment light from the
scene's closed-form sky projected once per scene, and a tone map. Cost: a few hundred ops per pixel, about
0.1–0.5 ms per 512² frame. Nothing is baked in; a scene fixes its look only by writing its own style.

**A style is an arbitrary function of the full shading context** (position, normal, view, body coordinates, every
light, shadow lookups, time, the paint's channels). The lighting terms (direct per light, specular, shadow, ambient,
emission) are handed to it ready-made, so toon can band N·L and woodblock can print the shadow edge, but a style is
never limited to them: screen-space hatching, painterly marks and silhouette-changing outlines stay possible. A style
sees each light's unshadowed arrival and its shadow visibility separately, so ink can follow a shadow edge. In tier I
every part is graph and is interpreted; fixed code is only a faster path for the default parts, matched by hash.

**`pbr` is built from parts, each a plain function over expressions**, so any part can be swapped and every part runs
in all three backends (WGSL, the JS twin, the interpreter) and ports to another engine as plain maths:

```ts
export const pbr = (o: Partial<PbrParts> = {}): Style => ...   // defaults below; any part replaced by the author's own
type PbrParts = {
  distribution: (n_h: F, rough: F) => F;                        // ggx
  visibility: (n_l: F, n_v: F, rough: F) => F;                  // smithGgx
  fresnel: (v_h: F, f0: V) => V;                                // schlick
  diffuse: (ctx: ShadeCtx, n_l: F, rough: F) => V;              // lambert
  environment: (ctx: ShadeCtx, rough: F) => { diffuse: V; specular: V };   // closed-form sky
  tone: (c: V) => V;                                            // aces
};
style: pbr({ fresnel: thinFilm(380) })                          // swap one part
style: { ...pbr(), ink: myInk }                                 // or override any field of the Style record
```

The parts are slots that take functions, not option menus. An author can skip `pbr` entirely and call `ggx`,
`schlick` or the light fold (`term` + `combine`, `src/light.ts`) inside their own `shade`.

The environment weight is a slot too: by default it integrates the given `distribution` and `visibility` at build
time, so swapping a lobe changes the reflected sky to match. Water and ground are overridden by spreading the record
(`{ ...pbr(), water, ground }`).

Inherited: GGX/Smith/Schlick, split-sum style environment light. New: the closed-form sky projected once per scene at
its default sun and time 0 (a sky that reads time or a param is refused by name); looks as functions over separated
terms with the full context still open.

## 5. Motion

Motion is any expression of time. The library offers three ways to produce a curve; all return ordinary expressions
the model can edit and compose:

- **Equations**: anything the model writes (polynomials, springs, closed-form ballistics).
- **Keys** (exist: `keys`, `ramp`, `through`, `ease` in `src/curve.ts`): interpolation between poses.
- **`solve`** (new): constraints become a curve, solved once at build time on the CPU.

```ts
const leap = solve({
  over: [0, 1.4], vary: { x: spline(8, roughX), y: spline(8, roughY) },
  hold: ({ x, y }) => [
    equal(vec2(x, y), [0, 0], { from: 0, to: 0.3 }),   // planted
    equal(vec2(x, y), DECK, { at: 1.2 }),              // lands
    atLeast(clearance(x, y), 0.05),                    // clears the rail
  ],
  prefer: { jerk: 1 },
  budget: { ms: 2000 },
});
leap.curves.x                         // an ordinary expression of time
export const checks = leap.holds;     // the same holds, proved over time
```

`solve` is local: it starts from `spline(n, from)`, which picks the side of each obstacle. A failed search is
`unsolved` (with the fix); `infeasible` is reserved for a certified contradiction; a NaN hold is `unreadable`. Solves
take a budget and are cached by their structural hash. Two independent rounds (Astra #1, Fable N1) put this first; the
owner's correction applies: the solver is one source of curves, not the motion model.
Rigid parts stay rigid between keys (rotation about a hinge, not blended solids), which avoids the swelling and
creasing every space-time-hull design had.

## 6. Checks: ranged and graded

**What they are for.** Checks are a tool for the author (prove a jaw clears a wall, a leap lands), not the training
reward, which is mainly aesthetic. They must never report something false. Ranged checks are `always` and
`eventually` over a leaf range (`src/ranged.ts`); the sampled checks (`staysClear` and the rest, `src/check.ts`) are
unchanged and still sample at 60 Hz.

```ts
export const checks = [
  always([time, 0, 4], ge(gap, 0.1)),                                  // every t, not sampled t
  always([speed, 4, 6], eventually([time, 0, 2], ge(landed, 0))),     // every launch speed
];
```

Each result: `{ holds: true | false | undecided, margin, bounds, witness: { t, params }, work, stop }`. `margin` is
the signal-temporal-logic robustness (how far from failing, signed); `witness` is where it is smallest. Undecided
always carries a reason (a budget in ms or boxes, a refused operator, `recur`, a margin within precision of 0) and is
never printed as a failure.

**Method.** Interval evaluation of the graph on the CPU (sound enclosures per operator; an operator that cannot be
bounded usefully is a typed refusal naming it), branch-and-bound over (t, params), interval Newton or bisection to
place the witness. Combinators `always`, `eventually`, `and`, `or` with robustness semantics. Proofs are about the f64
twin with f32-encoded held values; a range end may not depend on a bound leaf.

**6.3 Later: over player inputs.** A boss whose attack can be cancelled: prove the shortest warning across every
permitted input sequence. Needs inputs as bounded signals; designed after 6.1 lands.

**6.4 Later: picture facts without pixels.** Exact visible share and silhouette change from analytic visibility
(Fable N3), tested first against creative's 26 labelled motion cases.

**6.5 Arithmetic contract.** State what each proof is about (reals, the f64 twin, or f32 rendering). Later, an
f32-padded enclosure mode that bounds the GPU's value. Correctly rounded transcendentals alone do not make the twin
and GPU agree (contraction and f32 stores also differ), so they are an experiment, not a promise.

## 7. Model-facing tooling

- `loft context` stays the one brief; new API enters it only when final.
- **One question command** (Fable N5, cut down): `loft check --at t=…,param=… --explain` gives the margin at a
  setting, the witness, and the graph nodes driving it. No separate `measure`/`why`/`try`.
- The cache key is the exact structural hash of the interned graph. Equality saturation is not planned: reordering
  floating-point maths changes pixels.

## 7b. Extensibility contract

Every layer takes the author's own code, and the library's version of each is written in the same public terms:

| Layer | The author's own | Today |
|---|---|---|
| Geometry | a `Drawable` (`draws`, `forms`), a field for `march`, a `hit` for `draw.traced`, `draw.mesh` | yes |
| Paint | any channel word, read by any style | yes |
| Style | a `Style` record (`shade`, `ink`, `mark`, `outline`, `water`, ...) or a spread override of a library one | yes |
| Lighting | `pbr` parts; the light fold's `term` and `combine` | parts: new |
| Lights | a light as a function of a world point | yes (`lamp`) |
| Motion | any expression; `keys`; `solve` constraints as any expression ≥ 0 | `solve`: new |
| Checks | any expression of (t, params) as a margin; the ranged machinery works on it | ranged: new |
| Passes | another camera's picture (`pass`), post passes of a style | yes; a new kind of pass needs a library change |
| State | `recur` | renders through `loft build` only; checks report `undecided: recur`; a bake in serve later |
| Training surface | everything public | creative's allowlist was 37 hand-picked names; now generated from Loft's exports minus a reasoned denylist |

Two honest limits. Raw WGSL is opaque to the twin: it renders (tier C) but checks and `solve` cannot read it, and a
ranged check over it returns `undecided` naming the raw function. The host's frame structure (pose, draws, outline,
post) is fixed; a genuinely new stage is a library change, not scene code.

**Frozen (18 Nov):** tier I (the interpreter). Derived ceiling: it saves at most the warm 0.3–0.6 s of driver work, never the 1–1.5 CPU s compile child, and a folded march interprets at 33–410 ms a frame, slower than compiling; the disk cache and the warm compile worker beat it. f16 (`--precision mixed`) stays opt-in and frozen: no gain on the M4 and it reaches only post passes.

**If step 7 fails** (Loft does not beat three.js on looks): keep the checks, `solve`, the twin and `loft serve` as a
library that also serves three.js scenes, and stop growing Loft's authoring surface.

## 9. Not doing

- Space-time convex hulls as the geometry representation (ten designs; the exact-contact benefit comes from step 1
  on today's expressions without a new representation).
- Bevy as the authoring layer (Rust builds per sample, API churn, mutable world). It may be a tier-C target for Keel later.
- A path tracer. Revisit only if stills need bounced light; `march` and `draw.traced` remain for authors who want one.
- New names for convenience. Every addition above buys something the model could not otherwise do.
- Checks or `solve` as the training reward; the reward is mainly aesthetic.
- Background tier promotion in training; equality saturation as a cache key.
